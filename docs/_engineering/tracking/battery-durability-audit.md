## 0. Executive verdict

| Workout shape | Safe today? | Why (evidence) |
| --- | --- | --- |
| **Short, foreground, screen on** (≤ ~1 h, phone in hand or mounted, screen kept awake by the user) | **Yes** | One acceptance policy feeds metrics/map/persistence; Finish is deduplicated (`prov:391-403`), the save is one SQLite transaction that is idempotent per `(user_id, client_sync_id)` (`db:231-251`, unique index `db:1618-1621`), owner is re-checked at save (`repo:57-63`, `db:205-211`), and a failed save keeps the workout in memory with Retry/Discard (`prov:614-645`, `track:277-289`). Residual risks: process death before Finish (memory-only, `prov:57-72`), and "Finish & logout" / forced auth loss deleting the just-saved unsynced row (`SYNC-01`, §3.2 D-03). |
| **Screen-off** (phone in pocket, screen timeout, lock button) | **No** | No foreground service, no `FOREGROUND_SERVICE_LOCATION`/`POST_NOTIFICATIONS`, no wake lock (`manifest:3-6`, `MainActivity:7-12`, `svc:81-90`). Once no Activity is visible a while-in-use app stops receiving fixes *(platform inference)*; the 1-s wall-clock timer keeps counting (`prov:720-740`), so on return the workout shows inflated time and a zero-distance bridge across the gap (`policy:208-216`). If the OS kills the cached process, or the user swipes the task away (Activity destroyed ⇒ FlutterEngine destroyed, [design §2.4 items 7–8](./android-background-tracking-design.md)), the whole workout is lost with no notice on the next launch. |
| **Multi-hour** (2–4 h, thousands of points) | **Works only screen-on; degrades** | Feasible only if the user keeps the screen on for the whole session (see above), so the display dominates battery. App-side cost grows linearly per second and per point: the Track screen and the whole map rebuild every second because both watch the entire state (`track:113`, `map:357`), and flutter_map discards its projection/simplification cache on every rebuild (`flutter_map-8.3.1/lib/src/layer/shared/layer_projection_simplification/state.dart:52-58`); the map re-segments and rebuilds every polyline per point (`map:151-181`); follow mode leaks two animation status listeners per point (`map:671-696`, §2.4 B-05), giving O(n²) `MapController.move` calls over the session. Memory is fine at the point counts reachable at 5 s (≈2,900 points in 4 h). |

Three things this audit adds beyond the GPS audit and the IP-3.4 design: (a) the **follow-mode listener leak** (B-05) and the **flutter_map cache invalidation per second** (B-04) as concrete, fixable per-second costs; (b) a **10-second TCP probe to a public DNS server for the life of the process** (B-03), which is the app's largest non-GPS steady-state radio cost and would survive into a foreground-service workout untouched; (c) durability facts from platform source — **sqflite runs the database in `TRUNCATE`/`synchronous=FULL`** on AOSP (B-11; matters once IP-3.1 writes per point) and **Android's default corruption handler deletes the database file** (D-07). It also corrects two statements in the sibling docs from a locally built merged manifest (§7).

## 1. What the current design does (one paragraph)

`LiveTrackingNotifier` owns the whole active workout in Riverpod memory (`prov:57-72`): `WorkoutTimeline`, accepted points list, anchors, unsaved-completed entity. Start subscribes to `LiveTrackingService.instance.locationStream` and calls `Geolocator.getPositionStream(LocationSettings(accuracy: best, distanceFilter: 5))` (`prov:259-264`, `svc:81-90`), which on Android is `PRIORITY_HIGH_ACCURACY`, interval 5000 ms, min-update interval 5000 ms (API 33+; fastest 2500 ms below), min displacement 5 m (`geolocator_android-5.0.3/…/LocationOptions.java:21-60`, `…/FusedLocationClient.java:96-146`). Each accepted point copies the list and publishes a new state (`prov:689-702`); a 1-s `Timer.periodic` publishes elapsed time from the wall clock (`prov:720-740`). Pause cancels the timer but leaves GPS running (`prov:300-339`). Finish closes the timeline, cancels the subscription, computes completion metrics, then performs the **first and only SQLite write** — one transaction inserting the workout row, all points in one batch, and all status events (`prov:405-515`, `db:201-311`) — and fires sync (`repo:72-74`). There is no checkpoint table (`db:138-198`), no lifecycle hook other than sync-on-resume (`main:57-61`), no foreground service, receiver, or Kotlin beyond a 10-line Activity (`MainActivity:7-12`), and no wake lock (`grep -ri wakelock lib android` is empty).

## 2. Audit 1 — Battery and performance

### 2.1 GPS configuration and suitability per activity

| Item | Value in code | Assessment |
| --- | --- | --- |
| Accuracy | `LocationAccuracy.best` → `PRIORITY_HIGH_ACCURACY` (`svc:67`, `FusedLocationClient.java:132-146`; `best` and `high` map to the same priority on Android) | Correct for a route recorder. GNSS stays powered for the whole request regardless of interval; the interval mostly changes CPU/callback/write count, not receiver power *(platform inference)*. |
| Interval | not set in Dart ⇒ plugin default **5000 ms**, min-update interval 5000 ms on API 33+ (`LocationOptions.java:23,59`; `FusedLocationClient.java:105-107`) | Reasonable default. Point spacing at typical speeds: walking/hiking ≈ 7 m, running ≈ 15 m, cycling ≈ 40 m at 30 km/h. |
| Distance filter | 5 m (`svc:68`, `setMinUpdateDistanceMeters`, `FusedLocationClient.java:108`) | Suppresses most stationary jitter samples (fewer callbacks — good for CPU). Interaction to be aware of: standing still > 30 s then moving makes the next point a fresh anchor with zero bridge distance (`policy:208-216`), so the first few metres after every long stop are dropped; GPS-audit F5/F6 own the accuracy semantics — the point here is that the filter is what makes stops look like gaps. Device evidence is MC-1.5's job. |
| Per-type profile | one profile for running/walking/hiking/cycling | Fine for run/walk/hike. **Cycling** at 5 s cuts corners (≈40 m chords) and slightly under-counts curvy routes; a 2–3 s interval for cycling only would fix it at 1,200–1,800 points/h — still under the backend's 12,000-point cap for a 4 h ride at 2 s (7,200), but a 1 s interval crosses the cap in ~3.3 h (`SYNC-05`, GPS audit F14). Do not tighten below 2 s anywhere until IP-4.2/SYNC-05 lands. |
| `forceLocationManager` / `useMSLAltitude` | defaults (false) | Correct — FLP fusing is lower power than raw `LocationManager`. |
| One-time fixes | `getCurrentPosition(high, 10 s)` at map init on every app open and on "centre" (`svc:121-133`, `map:76-81`, `map:552`) | A GNSS spin-up at every launch on the default (Track) tab, without a workout. Small; also the out-of-context permission prompt (GPS audit F10). `getLastKnownPosition` first would avoid most of it. |

### 2.2 Paused workouts

Pause cancels only the elapsed timer (`prov:315-316`). It does **not** call `stopTracking()` — the fused request stays at high accuracy every 5 s for the whole pause, and paused samples still flow through the notifier as "markers" (`prov:671-675`), which the map turns into marker updates and, in follow mode, an 800 ms camera animation each (`map:369-378`, `map:124-126`, `map:651-699`). A 20-minute coffee stop is 20 minutes of GNSS drain plus map work for nothing. The acceptance policy already makes stopping GPS on pause safe: the first resumed point becomes a zero-distance anchor (`policy:188-196`) and any cached fix older than the resume boundary is rejected (`policy:159-166`), which is exactly what a warm restart of the stream would emit. The IP-3.4 design's requirement R5 ("Pause stops expensive high-accuracy updates") makes the same call.

### 2.3 Screen-off / background behaviour and the foreground-service implication

Today (`manifest:3-6`, `MainActivity`): no `FOREGROUND_SERVICE_LOCATION`, no `POST_NOTIFICATIONS`, no service, no wake lock, `permission_handler` present in the lockfile but not imported under `lib/`. What happens when the screen turns off *(platform inference from Android's location access rules; not device-verified)*:

1. The Activity stops; the app has only while-in-use location, so FusedLocation stops delivering; the request stays registered.
2. The Dart isolate keeps running while the process is cached: the 1-s timer (`prov:720-740`), the 10-s connectivity probe (`conn:52-55`), Riverpod emissions. No frames are pumped, so widget work is deferred — cheap. Dart timers cannot wake a sleeping CPU by themselves (no alarm), so their cost stays bounded until something else — a wake lock, or a foreground service that keeps the process active — keeps the CPU awake; then the probe becomes a real periodic radio cost.
3. Android 12+ may freeze the cached process; low memory may kill it or destroy only the Activity — with today's non-cached engine that destroys the isolate and the workout ([design §2.4 items 7–8](./android-background-tracking-design.md)).
4. On return, elapsed time is correct wall-clock but includes the gap; the gap becomes a new segment with zero bridge distance; pace and average speed are wrong.

The locally built **merged** debug manifest (`rythmrun_frontend_flutter/build/app/intermediates/merged_manifests/debug/processDebugManifest/AndroidManifest.xml`, a build artifact dated 2026-08-11) already contains `WAKE_LOCK` and `FOREGROUND_SERVICE` (lines 65-66, merged in from a transitive `androidx.work` dependency) and the two dormant `foregroundServiceType="location"` services from geolocator and the `location` plugin (lines 146-160). It does **not** contain `FOREGROUND_SERVICE_LOCATION` or `POST_NOTIFICATIONS`. So the platform-side gap for IP-3.4 is exactly those two permissions plus a service that is actually started, and — because a running location foreground service is what keeps the process out of the frozen/killed state — the *battery* effect of IP-3.4 is positive, not negative: it lets the user turn the screen off, which is by far the largest saving available (§2.7).

### 2.4 Wake locks

None today, which is correct for the current foreground-only design. For IP-3.4 the [design](./android-background-tracking-design.md) proposes a `PARTIAL_WAKE_LOCK` "iff state == active" (design §5.2, decision 4 "Accept; measure"). This audit recommends **no permanent partial wake lock** as the default:

- Fused location delivers each fix under the platform's own wake lock; a checkpoint write performed inside the callback completes while the CPU is awake. Nothing in the durable engine needs the CPU between fixes.
- Elapsed time is wall-clock derived (`timeline:141-157`), so a Dart timer that fires late after a CPU sleep self-corrects; the notification's elapsed time uses the system chronometer (design §5.5), needing no ticks.
- A partial wake lock held for a 4-hour workout keeps the AP awake continuously and turns B-03 (10-s probe) and B-06 (1-s timer) into real, continuous wake-ups. That is the classic "GPS app drains 20 %/h" pattern.
- If the device matrix shows missed fixes on a specific OEM, hold the lock only for the duration of the write, or enable it per-device as a documented exception. `WAKE_LOCK` is already in the merged manifest, so the permission cost is nil either way.

A *screen* wake lock ("keep screen on" during a workout) is a legitimate optional user toggle that many trackers offer; it is a product decision (§8), not a durability requirement, and it is the most expensive setting a user can enable.

### 2.6 Timers, network, and background work during a workout

- **1-s elapsed timer** (`prov:720-740`): required for the display; harmless while the process is cached; becomes a wake-up source only if a wake lock is added (§2.4).
- **10-s connectivity probe** (`conn:52-55` → `Socket.connect('8.8.8.8', 53)` with a 3-s timeout, `conn:93-107`), started once in `main()` (`main:24`) on a singleton and never stopped for the process lifetime (the provider's `onDispose` at `connectivity_provider.dart:13` stops the same singleton only if that provider is disposed). ≈360 TCP handshakes per hour on whatever radio is up; on cellular this keeps the radio cycling out of idle — a well-known drain unrelated to GPS. It runs during workouts, screen-off, and would run for the entire duration of a future foreground-service workout. STATUS already lists "polls public DNS" under IP-4.1 as a correctness item; it is also the app's largest steady-state non-GPS battery item.
- **Sync on every resume** (`main:57-61`): `syncAll` runs when the screen comes back mid-workout, including the paginated history restore if `history_restored` is false (`sync_coordinator.dart:52-60`). Network + CPU while GPS is running; deferrable until Finish.
- **Map tiles**: OSM raster tiles through flutter_map's `NetworkTileProvider`, which in 8.3.1 caches to disk by default (`BuiltInMapCachingProvider`, 1 GB cap, HTTP freshness; `tile_provider.dart:93-95`, `caching/built_in/built_in_caching_provider.dart`). Network use is therefore bounded to newly visited tiles (tens of KB each) and is independent of GPS cost. Tiles are requested only when the camera moves (follow mode, pans), including offstage. Nothing to fix for battery; the privacy-policy fact (third-party tile fetches) is already IP-5.6's item.
- **Ads**: no-op provider in every distributable build (IP-1.7); no SDK traffic.

## 4. Recommended low-cost architecture

This endorses the [IP-3.4 design](./android-background-tracking-design.md) §3–§7 as the target and keeps its schema, state machine, recovery policy, and channel contract. It records the pieces below so this audit stands alone, and it states three departures.

1. **Durable active-workout checkpoint** — SQLite v7, three tables (`active_workout_checkpoints` with `UNIQUE(user_id)` and `UNIQUE(user_id, client_sync_id)`, `active_tracking_points` keyed `(checkpoint_id, sequence)`, `active_status_events`), all reads and mutations user-scoped, timestamps UTC, forward-only migration ending in `foreign_key_check` like v6 (design §7.1). Start inserts `starting` **before** GPS starts and commits `active` after; pause/resume/finish/discard write immediately; `recoverable` is derived (any row for the current user at isolate start is an orphan).
2. **Bounded point buffering and flushing** — write each accepted point synchronously in one small transaction (`INSERT OR IGNORE` point + aggregate/sequence update) plus a 5-s heartbeat `UPDATE last_flushed_at`; at the current ≥5 s cadence this already meets IP-3's "≤5 points / ≤5 s" objective with no buffering code. If the device matrix shows write cost mattering, buffer ≤5 points behind the same DAO call and flush on the 5-s timer, pause, finish, lifecycle change, or stop; never buffer transitions. **Before shipping per-point writes, decide B-11 (WAL)** — it halves the fsync cost of every checkpoint for one manifest line.
3. **Atomic finalization** — Finish: stop points, close an open pause, set `finishing`, recompute metrics from durable rows (IP-1 unit contract), then **one transaction**: insert `workouts` + `tracking_points` + `status_changes` (sharing the private insert with `saveWorkoutInLocalDatabase`, refactored to take a `DatabaseExecutor`), delete the checkpoint (children cascade). The existing unique index makes retry idempotent; a `finishing` orphan with a matching completed row is cleaned, without one it offers Retry Finish/Discard, never Resume into a second route. Sync starts only after commit (already the case, `repo:66-74`). `SYNC-01` (a)+(b) must land first or the durable finalize is undone at logout (D-03).
4. **Android foreground service** — started only from a visible Start/Resume, type `location`, `START_NOT_STICKY`, `stopWithTask=false`, stopped on Finish/Discard/teardown/fatal permission loss, never outliving the engine (plugin detach ⇒ `stopSelf`; startup `stopIfRunning()`); permissions `FOREGROUND_SERVICE` (explicit), `FOREGROUND_SERVICE_LOCATION`, `POST_NOTIFICATIONS`; no `ACCESS_BACKGROUND_LOCATION`, no boot receiver, no battery-optimization prompt (design §5.1, §7.7). Keep the FlutterEngine cached while the service runs (design §4.3) so swipe-away cannot leave a lying notification (D-02). **Departure 1:** no permanent partial wake lock by default (§2.4); measure first. **Departure 2:** GPS stops on pause and restarts on resume inside the still-running service (also B-02 today, before any service exists). **Departure 3:** the 1-s elapsed tick is gated by app lifecycle (B-06); the notification's elapsed time comes from the system chronometer, so nothing needs a tick in the background.
5. **Notification lifecycle** — created with the service at Start (`IMPORTANCE_LOW`, silent, ongoing, `FOREGROUND_SERVICE_IMMEDIATE`), content derived only from committed durable state (type · chronometer elapsed · formatted distance, no coordinates), updated on transitions and at most every ~15 s while active, actions Pause/Resume/Finish optional and applied through the same engine transitions (idempotent against the row), body tap opens the Track tab only when the session is authenticated and owns a live/orphan checkpoint, removed with the service. `POST_NOTIFICATIONS` denial does not block the workout; the UI says so honestly (design §5.5, §7.7).
6. **Recovery flow after interruption** — at isolate start and after `activateUserScope(userId)`: `stopIfRunning()`; query only the current user's checkpoint; reconcile deterministically (`active` ⇒ append `interrupted @ last_flushed_at`, become `paused` — unknown downtime never counts as active; `paused` ⇒ stays open; `starting` ⇒ Resume/Discard only; `finishing` ⇒ complete-or-Retry); show exactly Resume / Finish / Discard; never auto-resume; foreign checkpoints invisible; a corrupt row is preserved with a stable error code (design §7.5). Teardown treats an orphan checkpoint as an active workout (D-011).
7. **Battery specifics that ride along** — B-02 (pause stops GPS), B-03 (remove the 10-s probe), B-04/B-05 (select-based rebuilds, incremental polylines, listener leak), B-06 (tick gating), B-09 (per-type interval only after SYNC-05). None of these changes route reliability: the acceptance policy is untouched, and the persisted route stays full-fidelity — sampling/simplification remains a rendering concern (IP-3.5 item 3).

What *not* to build (unchanged from the sibling docs): no second isolate, no WorkManager, no `ACCESS_BACKGROUND_LOCATION`, no `flutter_foreground_task` unless the own-service path fails the device matrix, no runtime kill switch that falls back to memory-only tracking, no Kotlin access to SQLite.

## 10. Top five highest-value changes, in priority order

1. **IP-3.1 + IP-3.2 — durable checkpoint and finalize-exactly-once** (PR-1, PR-2a, PR-2b): closes every silent-loss row in §3.1 (#1–#4, #6–#8, #12, #13, #17), bounds loss to ≤5 s, keeps `(userId, clientSyncId)` idempotency, and is the precondition for everything below.
2. **`SYNC-01` (a)+(b) before PR-2b** (D-03): a few hours of work that stops "Finish & logout"/forced loss from deleting the workout the previous step just made durable.
3. **IP-3.4 foreground service with cached engine, no `ACCESS_BACKGROUND_LOCATION`, and no permanent wake lock** (PR-4a/4b): the only change that lets users turn the screen off — simultaneously the largest battery saving available and the fix for the largest data-loss class.
4. **B-1 + B-2 — stop GPS on pause and remove the 10-second DNS probe**: two tiny, schema-free PRs that cut GNSS time during pauses and ~360 radio wake-ups per hour today, and keep a future foreground-service workout from carrying that cost for hours.
5. **B-3 + B-4 (+ PR-6) — fix the follow-mode listener leak and stop rebuilding the whole map every second**: removes the O(n²) growth and the per-second re-projection/simplification that make multi-hour, 10 000-point sessions jank, without touching the acceptance policy or persisted route fidelity.
